OpenAI just revealed something most people missed.

Their internal agent orchestrator, the system that generates 1M+ lines of code and processes 1 billion tokens per day, is built on Elixir.

Not Python. Not TypeScript. Elixir.

The model itself chose it. BEAM's process supervision, fault tolerance, and lightweight concurrency are exactly what AI agents need.

This is validation for every Elixir developer who's been saying "OTP already solves this." The patterns Python agent frameworks are building (isolated state, message passing, supervision, fault recovery) were shipped in Erlang in 1986.

We've been building Alloy, an open-source agent harness that makes it easy to build AI agents on the BEAM. It's not an orchestrator like Symphony. It's the engine inside each agent. The completion-tool-call loop, provider abstraction, and OTP integration so your agents survive production.

- Structured output you can trust. Force the model to call a specific tool before it can finish, so you get validated data every time.
- Human-in-the-loop that actually works. Middleware can inspect AND rewrite tool arguments before execution.
- Auto-recovery when context gets too large.
- About 7,500 lines with 3 runtime dependencies.

If you're building agents that need to stay running in production, the BEAM is where they belong.

## ElixirForum Post

Title: Alloy v0.10 - 6 providers, structured output enforcement, HITL editing

Body:

Hey everyone! Quick update on Alloy, the minimal agent harness.

Context: OpenAI recently revealed their multi-agent orchestrator (Symphony) is built on Elixir. The model itself chose it for BEAM's supervision capabilities. Symphony is the orchestration layer that coordinates fleets of agents. Alloy operates one level down. It's the engine inside each individual agent. The completion-tool-call loop, provider abstraction, and OTP integration. Different layer, same thesis: the BEAM is a natural fit for AI agent workloads.

What's new in 0.10:

3 new providers - Alloy now supports 6 providers: Anthropic, OpenAI, Gemini, xAI, Codex, and any OpenAI-compatible API (Ollama, DeepSeek, etc.). Swap with one line:

```elixir
# Switch from Claude to Grok. Change one line.
{:ok, result} = Alloy.run("Summarize this code",
  provider: {Alloy.Provider.XAI,
    api_key: System.get_env("XAI_API_KEY"),
    model: "grok-4"
  },
  tools: [Alloy.Tool.Core.Read]
)
```

`until_tool` for structured output - Instead of hoping the model returns valid JSON, define a tool with the exact schema you want and set `until_tool: "submit_answer"`. The loop won't complete until the model calls that tool. The schema is validated at the API level. No parsing, no prayer.

```elixir
{:ok, result} = Alloy.run("Analyze this data",
  provider: {Alloy.Provider.Anthropic, api_key: key, model: "claude-sonnet-4-6"},
  tools: [SubmitAnalysis],
  until_tool: "submit_analysis"
)
```

HITL `:edit` variant - Middleware can now return `{:edit, modified_call}` from `:before_tool_call` to rewrite tool arguments before execution. Previously you could only block or allow. Now you can correct a file path, sanitize a command, or enforce policy without stopping the agent.

```elixir
def call(:before_tool_call, state) do
  call = state.config.context[:current_tool_call]
  if dangerous?(call), do: {:edit, sanitize(call)}, else: state
end
```

Tool safety - Tools declare `concurrent?/0` (safe to parallelize?) and `max_result_chars/0` (output cap). The executor handles the rest. Plus automatic recovery when context gets too long: forces compaction and retries instead of failing.

Numbers: 568 tests, 0 failures. About 7,500 lines of code. 3 runtime dependencies. MIT license.

Full changelog: https://github.com/alloy-ex/alloy/blob/main/CHANGELOG.md

Feedback welcome, especially on the `until_tool` pattern. Curious how others are handling structured output from agents.
